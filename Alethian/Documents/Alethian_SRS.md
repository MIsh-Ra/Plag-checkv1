## 1. Introduction

### 1.1 Purpose
The purpose of this document is to define the functional and non-functional requirements for **Alethian**, a Local-First Research Integrity System. Alethian is designed to replace traditional plagiarism checkers by offering a privacy-centric, explainable platform that validates citations, detects peer-to-peer copying, identifies systematic web plagiarism, and analyzes authorship style without exposing institutional data to third-party commercial vendors.

### 1.2 Scope
Alethian is a self-hosted web application deployed on institutional hardware. It processes academic documents (PDFs) through a multi-stage pipeline:
1.  **Ingestion:** Hybrid extraction of text and structure.
2.  **Reference Validation:** Verification of citations against the global scholarly record via an API Mesh.
3.  **Internal Similarity:** Comparison against a private, local archive of past student work.
4.  **Web Dragnet:** Targeted search of suspicious content against the open internet.
5.  **AI Forensics:** Statistical analysis of text perplexity to detect machine-generated content.
6.  **Presentation:** A decoupled dashboard for faculty review.

### 1.3 Definitions, Acronyms, and Abbreviations
* **API Mesh:** The orchestration of multiple open-science APIs (Semantic Scholar, Unpaywall) to validate data without local storage.
* **Hallucination:** A non-existent reference generated by an AI model.
* **LSH (Locality Sensitive Hashing):** An algorithm used for rapid near-duplicate document detection.
* **Binoculars Metric:** A zero-shot method for AI detection comparing two language models.
* **Source Coherence:** The detection of multiple copied text chunks originating from a single un-cited domain.
* **SPA:** Single Page Application (React.js).

## 2. Overall Description

### 2.1 Product Perspective
Alethian operates as a standalone system within the university's intranet. It interacts with:
* **Internal Storage:** For archiving past theses.
* **External APIs:** Semantic Scholar, Unpaywall, Serper.dev (Transient data only).
* **LMS (Future Scope):** Potential integration with Moodle/Canvas.

### 2.2 User Classes and Characteristics
* **Faculty/Reviewers:** Access detailed reports, toggle forensic layers, and make final academic judgments.
* **Administrators:** Manage system configuration, API keys, and user access roles.
* **System:** Background service accounts handling ingestion and processing.

### 2.3 Operating Environment
* **Server:** Ubuntu 24.04 LTS (High-Performance "Fat Node").
* **Client:** Modern Web Browsers (Chrome, Firefox, Edge).
* **Network:** Institutional Intranet (Local-First).

## 3. System Features (Functional Requirements)

### 3.1 Layer 1: The Ingestion Engine
**Description:** Converts unstructured PDF binary data into normalized JSON.
* **FR-1.1:** The system shall accept PDF file uploads up to 100MB.
* **FR-1.2:** The system shall utilize **Grobid** as the primary parser for structured extraction.
* **FR-1.3:** If Grobid confidence is `< 0.8` (e.g., scanned images), the system shall automatically route the document to **Llama-3-Vision** for OCR processing.
* **FR-1.4:** The system must normalize output into a JSON structure containing: `Title`, `Authors`, `Abstract`, `Body_Text` (indexed by page), and `References_List`.

### 3.2 Layer 2: Reference Validation (The API Mesh)
**Description:** Validates the existence, status, and accuracy of citations.
* **FR-2.1:** For every extracted citation, the system shall query the **Semantic Scholar API**.
* **FR-2.2:** If the API returns "Not Found," the system shall flag the citation as a **"Potential Hallucination."**
* **FR-2.3:** The system shall check the `is_retracted` metadata field and flag **"Retracted Source Cited"** if true.
* **FR-2.4:** The system shall attempt to retrieve the abstract via Semantic Scholar or Unpaywall and calculate **Cosine Similarity** against the student's citing sentence. Mismatches (`score < 0.4`) shall be flagged as **"Citation Misrepresentation."**

### 3.3 Layer 3: Internal Similarity (The Memory)
**Description:** Detects plagiarism against the local archive of past submissions.
* **FR-3.1:** The system shall generate a **MinHash Signature** for the document and query the **Redis** database for near-duplicates (>90% similarity).
* **FR-3.2:** For paragraphs not caught by MinHash, the system shall generate vector embeddings and query the **Qdrant** database to detect semantic paraphrasing.

### 3.4 Layer 4: Web Dragnet (The Hunter)
**Description:** Detects systematic copying from the open web.
* **FR-4.1:** The system shall isolate "Suspicious Chunks" (text with low perplexity or style anomalies) that were not found in Layer 3.
* **FR-4.2:** The system shall query **Serper.dev** with these chunks.
* **FR-4.3:** The system shall perform **Source Coherence Analysis**: if >3 chunks map to the same un-cited domain, the submission is flagged for **"Systematic Web Plagiarism."**

### 3.5 Layer 5: AI Forensics (The Judge)
**Description:** Analyzes authorship style to detect AI generation.
* **FR-5.1:** The system shall compute the **Binoculars Metric** using a local LLM setup (Llama-3 + Falcon-7B).
* **FR-5.2:** The system shall generate a **Perplexity Plot** and a **Burstiness Score**.
* **FR-5.3:** The system shall **not** issue a binary "AI Detected" label but instead highlight "Statistically Anomalous" regions.

### 3.6 Layer 6: Presentation (The Interface)
**Description:** Provides an interactive dashboard for analysis.
* **FR-6.1:** The frontend shall be a **React.js SPA** utilizing the **Shadcn/ui** component library.
* **FR-6.2:** The dashboard shall provide a **Side-by-Side Diff View**: clicking a flagged sentence on the left renders the source evidence on the right.
* **FR-6.3:** The system shall provide a **"Traffic Light" Reference Report** (Green=Verified, Yellow=Suspect, Red=Hallucinated).
* **FR-6.4:** Faculty shall be able to export a signed PDF summary of the report.

## 4. External Interface Requirements

### 4.1 User Interfaces
* **Web Portal:** Clean, minimalistic interface supporting Drag-and-Drop uploads.
* **Real-time Feedback:** WebSocket integration to display a live progress stepper (e.g., "Checking Web Sources... 45%").

### 4.2 Software Interfaces
* **Backend API:** FastAPI (Python 3.12) exposing REST endpoints.
* **Database Interface:** * **Qdrant** (gRPC) for Vector Search.
    * **Redis** (TCP) for Caching/Queues.
    * **PostgreSQL** (TCP) for User Data.
* **External APIs:** HTTPS JSON calls to Semantic Scholar, Unpaywall, and Serper.dev.

### 4.3 Hardware Interfaces
* **GPU:** The system requires direct access to NVIDIA CUDA cores for Layer 1 (Vision) and Layer 5 (Forensics).

## 5. Non-Functional Requirements

### 5.1 Performance
* **Throughput:** The system shall process a standard 50-page thesis in under **5 minutes**.
* **Concurrency:** The system shall support a job queue capable of handling **50+ concurrent submissions** without service degradation.

### 5.2 Safety & Privacy
* **Local Sovereignty:** No student body text shall be transmitted to third-party storage or AI training providers.
* **Transient Analysis:** External API calls must use anonymous metadata snippets only.

### 5.3 Reliability
* **Availability:** The system shall maintain 99.9% uptime during the academic year.
* **Fault Tolerance:** If External APIs (Layer 2/4) are unreachable, the system shall degrade gracefully, completing the Internal Checks (Layer 1, 3, 5) and marking External Checks as "Pending."

### 5.4 Maintainability
* **Containerization:** All services shall be Dockerized and orchestrated via Docker Compose.
* **Modularity:** The API Mesh layer must be modular to allow swapping providers (e.g., switching from Serper to Brave Search) without core code changes.
